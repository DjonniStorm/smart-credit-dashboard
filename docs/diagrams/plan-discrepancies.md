# Расхождения кода и plan.md

Список составлен при построении диаграмм. Код не менялся, это только перечень. Если пункт закрыт в коде, его нужно убрать отсюда вместе с обновлением диаграмм.

## Статусы и переходы

- Таблицы допустимых переходов в коде нет. Единственная запись статуса: при создании заявки `in_review`. Проверки допустимости перехода нет ни в api, ни в интерфейсах, поэтому диаграмма переходов в [02-application-statuses.md](02-application-statuses.md) нарисована по `plan.md`.
- После скоринга статус заявки не меняется: рекомендация `decide()` пишется в событие, в `applications.scoring` и в `applications.decision`, заявка остаётся `in_review`.
- Словарей статусов четыре: хранимый (5 значений), публичный API (12, как в плане), статус интерфейсов (7, с `counter_offer` и `disbursed`) и этапы. Маппинг лежит в трёх `api-mapper.ts`.
- API всегда отдаёт `offerKind: initial`, поэтому `counter_offer` в интерфейсах недостижим. План требует `OFFERED` с признаком `isCounterOffer`.
- Интерфейсы сворачивают `SUBMITTED`, `VALIDATING`, `ACCEPTED`, `SIGNING` и `BLOCKED` в `in_review`: заблокированная заявка выглядела бы как «на рассмотрении».
- Заявка создаётся сразу в `in_review` (`UNDER_REVIEW`), минуя `DRAFT`, `SUBMITTED` и `VALIDATING`.
- Восемь внутренних стадий плана (`ENRICHING`, `SCORING`, `MANUAL_REVIEW` и другие) не заведены. В схеме есть семь других этапов (`intake`, `completeness` и так далее), АРМ выводит из них только `scoring` и `decision` по наличию `scoring`.
- Роли «старший менеджер» и действия `UNBLOCK` в коде нет.

## Команды сотрудника и клиента

- Команды АРМ в api не реализованы: `act` и `simulateClient` в `apps/backoffice/src/shared/api/arm/http-api.ts` выбрасывают ошибку. В кабинете принятие оффера, отказ, ответ на запрос и подписание отвечают 501. Демо-сценарии из `plan.md` по HTTP не проходятся дальше скоринга.
- Сотрудник не может войти: `AuthService.signIn` всегда выдаёт роль `client`, хотя `DemoSession` допускает `analyst` и `lead`.
- Кабинет показывает решение (`decisionOf`) при статусе `UNDER_REVIEW`, собирая его из `scoring.recommendation` с `ratePercent: 0` и `monthlyPayment: 0`. План такого вывода не описывает.

## Решение и автономность

- План задаёт уровни автономности `new`, `verified`, `stable`, `paused`. Они есть в `packages/contracts/src/autonomy.ts` и в `autonomy_policies` (во всех демо-политиках `stable`), а `decide()` выставляет режим `shadow` или `assist` из другого набора (`shadow`, `assist`, `controlled`) и политику не читает. `AutonomyStore` считает `eligibility`, но решение об автоодобрении она не меняет: `approve` определяется порогами `confidence` 0,8 и суммой 5 000 000.
- Порядок правил из `plan.md` (стоп-факторы, грейд D, расхождения, продуктовая пригодность, лимит) не совпадает с `decide()`: она смотрит на `risk_band`, `readiness_index`, рекомендацию модели и `confidence`.

## Данные и инфраструктура

- ЕГРЮЛ, ФНС и БКИ в плане отдельные синтетические моки. `apps/mocks` удалён, данные лежат в таблице `demo_sources` и читаются из базы.
- Seed (`pnpm --filter api db:seed`) запускается вручную и не входит ни в compose, ни в `apps/api/Dockerfile`. После `docker compose up` в базе нет демо-учёток, `demo_sources` и `autonomy_policies`, поэтому каждая задача скоринга падает с «Синтетические источники не найдены», а карточка АРМ с «Политика автономности не найдена».
- Схема объявлена в трёх местах: `001_workflow.sql`, `WorkflowStore.onModuleInit` и `scripts/seed-demo.ts`. Таблицы `demo_*` и `company_bki_consents` в миграцию не входят.
- Таблица `source_checks` создана, но код в неё не пишет.
- Отдельного процесса worker нет, очередь обрабатывается внутри api. Object storage в compose нет, `StorageService` пишет на диск. Событийного слоя (SSE, шина) нет. Alfi в api отсутствует.
- Сотрудники, продукты, демо-учётки и политики автономности хранятся jsonb-документами, нормализованных таблиц нет. Модель на уровне сущностей: [05-entity-model.md](05-entity-model.md).
