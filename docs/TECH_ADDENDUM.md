# Дополнение к плану: правки и контракты

Дополняет `smart-credit-dashboard-plan.pdf` (дальше «план»). Продукт, роли и механики берём из плана. Здесь только то, что план сознательно не фиксирует (стр. 7: «не выносятся внутренние команды, последовательности API, таблицы»), и правки, без которых сквозной сценарий или проверка ломаются.

Источник контрактов в коде: zod-схемы в `packages/contracts`. api отдаёт их через nestjs-zod, OpenAPI собирается из Nest, `packages/sdk` генерируется из OpenAPI. Документ и схемы должны совпадать; при расхождении правим оба.

### 2.3. Автономность

Уровни: `new`, `verified`, `stable`, `paused`. Ключ политики: продукт и диапазон суммы. Автоодобрение только при `stable`, грейде A, сумме не выше `maxAutoAmount`, без открытых расхождений, без флагов ручной проверки (стр. 6 плана). Предложение уходит клиенту сразу с `isHumanDecision = false`. `controlWindowMinutes` задаёт, сколько менеджер может перехватить его (`offered` → `under_review`); клиента окно не держит. При `new` и `verified` окно только подсвечивает просрочку в очереди.

## 5. Продукты и формулы

### 5.1. Продукты

Ставка = ключевая ставка ЦБ + `spreadPp` продукта + надбавка грейда (QA №35). Ключевая ставка в коде: 14 % с 11.09.2026, сверить с cbr.ru после заседания 23.10.2026. Каталог из кабинета PR #3; каталог АРМ из PR #3 удалить.

| `id`              | Цель                     | Сумма      | Срок, мес. | `spreadPp` | Залог                       | Мин. возраст, мес. | `maxDebtLoad` |
| ----------------- | ------------------------ | ---------- | ---------- | ---------- | --------------------------- | ------------------ | ------------- |
| `working_capital` | оборот, закупка          | 0,3–10 млн | 3–24       | 5          | нет                         | 6                  | 0,5           |
| `cash_gap`        | кассовый разрыв          | 0,1–3 млн  | 1–12       | 6          | нет                         | 6                  | 0,5           |
| `equipment`       | оборудование, транспорт  | 0,5–30 млн | 12–60      | 3,5        | приобретаемое имущество     | 12                 | 0,7           |
| `development`     | новая точка, направление | 1–20 млн   | 12–60      | 4,5        | поручительство собственника | 12                 | 0,6           |

При ключевой 14 % ставки 17,5–20 % для грейда A и до 24 % для C.

### 5.2. Scorecard (baseline, работает без ML)

Здоровье компании считается только по компании, рейтинг добавляет качество данных, готовность считается по заявке (стр. 2–3 плана, индексы независимы).

`T` = оборот по счёту в банке за месяц + принятый документами оборот из других банков.
`CF = 0,15 × T` (допущение о марже, в документации). `P_exist` = платежи по кредитам из БКИ. `DTI = P_exist / CF`.

| Фактор                             | Значения и баллы                                                           |
| ---------------------------------- | -------------------------------------------------------------------------- |
| срок работы                        | < 12 мес. −5; 12–36 мес. +4; > 36 мес. +9                                  |
| БКИ, макс. просрочка за 12 мес.    | история без просрочек +12; нет истории 0; 1–29 дн. −6; 30–89 дн. −16       |
| тренд оборотов                     | растёт +9; стабилен +5; падает −11                                         |
| `DTI`                              | < 20 % +8; 20–45 % +2; 45–65 % −8; > 65 % −18                              |
| налоги                             | долга нет +5; долг без блокировки −4                                       |
| качество данных (только в рейтинг) | открытое расхождение −9; факт без подтверждения −3 за каждый, не больше −9 |

- `healthIndex = clamp(50 + Σ факторов компании, 0, 100)`
- `score = clamp(healthIndex + Σ качества данных, 0, 100)`
- Грейд: A ≥ 70, B 55–69, C 42–54, D < 42. Надбавка: A 0, B +2, C +4 п. п.
- `readinessIndex = max(0, 100 − 30·[нет обязательных полей] − 35·[открытое расхождение] − 25·[залог нужен и не подтверждён] − 20·[источник недоступен])`
- `pd` заполняет ML Руслана; baseline отдаёт `null`. Ответ scoring: `score`, `grade`, `healthIndex`, `factors[]` (значение, источник, дата, баллы), `pd`, `confidence`, `model`.

### 5.3. Компас

`self_declared`, `confirmed_single`, `confirmed_multi`, `discrepancy`, `manual_check`. Выручка: отклонение заявленной от `T` ≤ 15 % → `confirmed_single`, если ФНС тоже в пределах 15 % → `confirmed_multi`, больше 15 % → `discrepancy` и системный запрос клиенту. Залог с документом → `manual_check` до `review_evidence`. Источник `unavailable` → `manual_check`.

### 5.4. Лимит

- `P_max = max(0, CF / 1,25 − P_exist)` (DSCR не ниже 1,25)
- `i = ставка / 12 / 100`, `K = i(1+i)^n / ((1+i)^n − 1)`, `L_afford = P_max / K`
- `L_max = min(product.maxAmount, L_afford)`; долг после выдачи к годовой выручке не выше `maxDebtLoad`

### 5.5. Рекомендация (api, decision engine)

Правила по порядку, первое сработавшее решает:

1. Стоп-факторы → `reject`: компания не действует; `accountsBlocked`; текущая просрочка или просрочка ≥ 90 дн. за 12 мес.; грейд D.
2. Открытое расхождение, неподтверждённый залог, недоступный источник → `request_info`, системный запрос создаётся сразу.
3. Возраст меньше минимума продукта → `counter_offer` с подходящим продуктом, если такой есть, иначе `reject`.
4. `amount ≤ L_max` и `readinessIndex ≥ 80` → `approve`.
5. `amount > L_max ≥ product.minAmount` → `counter_offer`: при приоритете «сумма» сначала удлиняем срок до максимума продукта, иначе снижаем сумму до `L_max`.
6. Иначе → `reject` с причиной `debt_load`.

Грейд C и любые правила со статусом «требует ручного подтверждения» идут только через менеджера. Для каждого правила api отдаёт `pass`, `fail`, `manual`, `n/a` (стр. 6 плана).
