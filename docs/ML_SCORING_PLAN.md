# ML и scoring: план реализации

## Цель

Scoring оценивает риск и качество данных, а decision engine принимает объяснимое операционное решение. Модель не имеет права самостоятельно менять статус заявки, отправлять оффер или обходить проверки. Любое автоматическое действие проходит через policy engine и записывается в аудит.

## Архитектура

```text
источники и заявка
        ↓
нормализация + snapshot признаков
        ↓
baseline / ML scorer
        ↓
калибровка PD + confidence + факторы
        ↓
decision engine (детерминированные правила)
        ↓
recommendation + reasons + next_actions
        ↓
менеджер или контролируемая автономность
```

Scoring service остаётся заменяемым: baseline, обученная модель и будущая ensemble-модель реализуют один контракт `ScoreResponse`. Decision engine не зависит от библиотеки обучения и не принимает сырые вероятности без калибровки.

## Контракт результата

Минимальный результат расчёта:

```json
{
  "model": "rules-baseline-v2",
  "model_version": "2026-10-23",
  "score": 0,
  "grade": "A|B|C|D",
  "pd": 0.0,
  "risk_band": "low|moderate|high",
  "health_index": 0,
  "readiness_index": 0,
  "confidence": 0,
  "recommendation": "approve|counter_offer|request_info|manual_review|reject",
  "factors": [],
  "rules": [],
  "reasons": [],
  "next_actions": [],
  "feature_snapshot_id": "...",
  "computed_at": "..."
}
```

`score` — нормированный индикатор 0–100, `pd` — вероятность дефолта в горизонте, согласованном с датасетом. Эти величины нельзя называть гарантией одобрения или фактической вероятностью без калибровки на наблюдаемых данных.

## Слои признаков

1. **Юридические:** активность ЕГРЮЛ/ЕГРИП, возраст бизнеса, массовый адрес, право подписи.
2. **Денежный поток:** выручка, расходы, чистый поток, тренд, сезонность, DSCR.
3. **Долговая нагрузка:** текущий долг, платёж, нагрузка после выдачи, число активных кредитов.
4. **Поведение:** просрочка, максимальная просрочка, частота запросов, история погашения.
5. **Налоги и compliance:** налоговый долг, ограничения, расхождения источников.
6. **Заявка:** продукт, сумма, срок, обеспечение, полнота документов и согласия.

Все признаки имеют `source`, `observed_at`, `quality`, `missing_reason` и snapshot-идентификатор. Признаки, появившиеся после решения, запрещены для обучения и онлайн-расчёта.

## Baseline v2

До появления размеченной истории используется детерминированная модель:

- базовый балл 50;
- положительные/отрицательные вклады ограничены диапазоном и видны в `factors`;
- стоп-факторы не маскируются средним баллом;
- отсутствующий источник не получает положительный бонус;
- здоровье бизнеса и готовность заявки считаются отдельно;
- confidence уменьшается за отсутствующие источники, несогласованные факты и неподтверждённый залог;
- `pd` вычисляется только как демонстрационная монотонная проекция score, пока нет калибровочного датасета;
- baseline должен воспроизводиться по одному feature snapshot.

Пороговые значения, веса, продуктовые лимиты и ставки находятся в конфигурации policy engine, а не в UI.

## Decision engine

Правила применяются в фиксированном порядке:

1. критичный стоп-фактор → `reject`;
2. отсутствует обязательное согласие, источник или доказательство → `request_info`;
3. продукт или сумма не проходят, но существует допустимый диапазон → `counter_offer`;
4. ручной флаг, низкая confidence или серая зона → `manual_review`;
5. все правила пройдены → `approve`.

Каждое правило возвращает `pass`, `fail`, `manual` или `n/a`, ссылку на входные признаки и текст для сотрудника. Изменение рекомендации человеком требует причины.

## Переход к ML

В текущем коде реализован безопасный evaluation scaffold: temporal split без перемешивания,
отдельный calibration split, isotonic challenger, bounded metrics, PR-AUC/KS,
детерминированные bootstrap confidence intervals и quality gate. Пока нет
размеченного production-датасета, endpoint оценки намеренно выбирает champion при любой
неуверенности и оставляет challenger в shadow. Этот scaffold не считается обученной моделью и
не используется для автоматического одобрения.

### Этап 1: качество данных

- единая схема feature snapshot;
- data validation перед обучением;
- контроль пропусков, дублей, leakage и temporal split;
- синтетические профили для регрессионных тестов.

### Этап 2: интерпретируемая модель

Основной кандидат — градиентный бустинг по табличным признакам с монотонными ограничениями для очевидных зависимостей (просрочка, налоговый долг, долговая нагрузка). Контрольная модель — логистический scorecard. Модель выбирается не по одному AUC.

### Этап 3: калибровка и неопределённость

- временной holdout;
- Platt или isotonic calibration только на отдельном calibration split;
- Brier score, log loss, ECE и reliability curve;
- bootstrap interval для PD;
- low-confidence/out-of-distribution → `manual_review`.

### Этап 4: объяснения

Для менеджера храним top positive/top negative factors, значение признака, baseline, вклад, источник и timestamp. SHAP используется для model review и локального объяснения, но клиентский текст строится из проверенных шаблонов и policy reasons, а не из свободной генерации.

### Этап 5: автономность

Автономность включается только для связки `model_version + product + policy_version + amount_band`. Нужны закрытые расхождения, отсутствие ручных флагов, стабильная калибровка и контрольное окно перехвата. Любой drift, рост manual overrides или ухудшение calibration автоматически переводит связку в `paused`.

## Оценка качества

Обязательные метрики:

- discrimination: ROC-AUC, PR-AUC, KS;
- calibration: Brier, log loss, ECE, reliability;
- business: approval rate, bad rate, expected loss, counter-offer acceptance;
- operations: manual-review rate, SLA, source timeout rate;
- stability: PSI/CSI по ключевым признакам и drift PD;
- fairness: разница TPR/FPR и approval rate по разрешённым группам. Чувствительные признаки не используются для решения; группы применяются только для аудита.

В коде пока нет production training job, model artifact registry, group fairness отчёта и
автоматического drift worker: эти части требуют реального датасета, target definition,
разрешённых audit-групп и runtime-интеграции. Synthetic dataset используется только для
регрессионного smoke-теста и не является доказательством качества кредитной модели.

Порог качества фиксируется до эксперимента. Нельзя принимать модель по AUC при деградации calibration или росте отказов в отдельной группе.

## Reject inference

Отказы не являются автоматически размеченными дефолтами. До появления корректной схемы наблюдения нельзя обучать модель на наивно переобозначенных отказах. Нужны policy для champion/challenger, контроль принятой выборки и отдельный анализ selection bias.

## Версионирование и аудит

В каждом scoring event сохраняются `model_version`, `policy_version`, `feature_snapshot_id`, входы после нормализации, результат, причины и latency. Модель можно откатить по версии без изменения исторических решений. Пересчёт создаёт новое событие, а не переписывает старое.

## Безопасность

- PII не попадает в логи и prompt;
- feature snapshot доступен только по идентификатору;
- LLM не получает права менять score/status;
- документы и источники считаются недоверенными входами;
- ошибки модели ведут к ручной проверке, а не к автоматическому одобрению.

## Исследовательские основания

- [Calibration of Machine Learning Classifiers for Probability of Default Modelling](https://arxiv.org/abs/1710.08901) — calibration split и оценка вероятностей.
- [Approaches for credit scorecard calibration](https://www.sciencedirect.com/science/article/pii/S0950705117303568) — калибровка не меняет порядок score, но влияет на пригодность PD.
- [Reject inference methods in credit scoring](https://pmc.ncbi.nlm.nih.gov/articles/PMC9041715/) — ограничения эвристик по отказам и selection bias.
- [Enhancing ML Models Interpretability for Credit Scoring](https://arxiv.org/abs/2509.11389) — сочетание сильной модели с glass-box объяснением.
- [Monotonicity constraints in credit scoring](https://cadmus.eui.eu/bitstreams/3f2a40e5-0711-4388-acb7-74ae7b328af7/download) — компромисс точности и проверяемости монотонных моделей.
