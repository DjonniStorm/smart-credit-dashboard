# E2E smoke: клиентский кабинет

Smoke-проверка покрывает единый mock API и клиентские переходы. Все данные
синтетические, внешние сервисы не вызываются.

## Подготовка

1. Запустить клиент: `pnpm --filter client dev`.
2. Открыть `http://localhost:3000/login`.
3. Перед повторным прогоном очистить site data для `localhost:3000` или нажать
   «Сбросить демо-данные» в меню разработчика, если оно включено.
4. Войти под учёткой `ИП Столяров Дмитрий Олегович` для ветки запроса банка.

## Сквозной сценарий запроса, counter-offer и подписи

- [ ] Войти в кабинет и открыть «Новая заявка».
- [ ] Заполнить продукт, сумму, срок, финансы и добавить PDF/JPG документ.
- [ ] Отправить заявку; в списке и карточке видны номер, документ и статус
      «На проверке».
- [ ] Дождаться перехода в «Нужно уточнение»; в истории появляется событие
      банка, а форма ответа содержит обязательный текст и необязательный файл.
- [ ] Отправить ответ с файлом; повторная отправка того же запроса блокируется,
      документ появляется в `/documents`, заявка возвращается на проверку.
- [ ] Дождаться решения; при counter-offer рядом видны запрошенные и
      предложенные сумма/срок, ставка и платёж.
- [ ] Принять предложение; карточка показывает условия договора и ссылку на
      подписание. Отказ проверять отдельно: он переводит заявку в терминальное
      состояние и не оставляет активной кнопки принятия.
- [ ] Запросить демо-код, проверить ошибку на неверном коде, затем ввести
      показанный шестизначный код.
- [ ] После подписи увидеть «Выдача выполняется», затем после таймера —
      «Выдано» и счёт зачисления. В истории есть события клиента и банка.

## Стабильные селекторы для автоматизации

Интерактивные контрольные точки не зависят от русского текста:

| Точка                 | Селектор                                    |
| --------------------- | ------------------------------------------- |
| форма ответа банку    | `[data-testid="answer-request"]`            |
| отправка ответа       | `[data-testid="answer-request-submit"]`     |
| сравнение предложения | `[data-testid="offer-decision"]`            |
| принять условия       | `[data-testid="offer-accept"]`              |
| отказаться            | `[data-testid="offer-decline"]`             |
| демо-код              | `[data-testid="sign-demo-code"]`            |
| поле кода             | `[data-testid="sign-code"]`                 |
| подписать             | `[data-testid="sign-submit"]`               |
| ссылка документа      | `[data-testid="document-application-link"]` |

## Контрольные инварианты mock API

- UI не меняет статус локально: после каждой мутации он получает полный
  `Application` из `CabinetApi` и обновляет query-кэш.
- Ответ на запрос допустим только один раз; пустой текст отклоняется до вызова
  API.
- `acceptOffer`, `declineOffer` и `sign` идемпотентно отклоняют повторные или
  несвоевременные действия с HTTP-подобной ошибкой `409`.
- Файл ответа хранится в `request.answer.documents` и попадает в общий список
  документов.
- Демо-подпись не является реальной ЭП, а выдача не создаёт реальную
  проводку.
