# Альфи: план реализации

## Граница ответственности

Альфи — объясняющий помощник для клиента и сотрудника банка. Он выбирает безопасный следующий шаг, объясняет фактор или запрос и готовит черновик действия. Альфи не меняет статус, сумму, срок, продукт, score или решение без подтверждения пользователя/сотрудника.

## Контур ответа

Каждый ответ строится как:

```text
state → title → message → action → safety
```

Сначала формируется детерминированный fallback по `getAlfiGuidance`. LLM может только переформулировать `message` и `action` в разрешённых пределах. Если endpoint недоступен, возвращается fallback без деградации основного сценария.

## Контекст

В prompt передаются только нормализованные поля:

- роль и публичный статус;
- внутренний этап без PII;
- кто должен действовать;
- blocker и recommendation;
- подтверждённые факторы и открытые запросы;
- допустимые действия из policy engine.

Документы, токены, полные банковские выписки и сырые внешние payload не передаются модели. Для клиента внутренние стадии заменяются на безопасные пользовательские формулировки.

## Выходная схема

LLM обязан вернуть JSON:

```json
{
  "message": "...",
  "action": "...",
  "reasonCodes": ["missing_document"],
  "confidence": 0.0
}
```

Ответ валидируется по длине, JSON-схеме, разрешённым `reasonCodes` и списку действий. Свободные обещания сроков, одобрения, ставки или обхода проверки отбрасываются.

## Режимы

- `template`: текущий детерминированный fallback;
- `llm`: OpenAI-compatible endpoint из `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`;
- `shadow`: LLM генерирует ответ для оценки, но пользователю показывается template;
- `disabled`: только системные подсказки без модели.

Начинать с `shadow`, измерять полезность, запрещённые обещания, latency и fallback rate. В production-like демо включать `llm` только после прохождения валидации ответа.

## Инструменты

LLM не получает прямых write-инструментов. Для действия возвращается intent, который UI переводит в существующую доменную команду после явного подтверждения. Любая команда повторно проходит role/status/policy проверки.

## Оценка качества

- корректность следующего шага;
- отсутствие запрещённых обещаний;
- сохранение причин и чисел из policy engine;
- доля fallback и p95 latency;
- доля отклонённых JSON-ответов;
- полезность ответа по ручной разметке менеджеров;
- отсутствие утечки PII в логах и prompt.

## Эволюция

На первом шаге достаточно шаблонов и shadow-контуров. Далее можно подключать retrieval по справочнику продуктов и внутренним инструкциям, затем — модели с открытыми весами через заменяемый endpoint. Промпт, модель и temperature версионируются; история ответа и причина fallback сохраняются в audit.
